# 06 — Security: threat model and decisions

Document aimed at project maintainers. For the end-user guide, see `07-user-security.md`.

## Threat model

`picklock` is a local, single-user TUI that connects to databases the user brings themselves. There's no server, no multi-tenancy, and no code that receives input from third parties beyond the keyboard. That's why the threat model is small and local:

| Threat | Risk | Current mitigation |
|---|---|---|
| Another user on the same machine reads saved passwords | High | `connections.json` with `0600` permissions (directory `0700`). Saving the password is optional. |
| Connection without TLS to a network database → MITM reads credentials and data | Medium-high | `SSL` field for every network engine, `prefer` by default (`require`/`verify-full`/`disable`), mapped to each driver's TLS options. |
| Accidental damage to production (`DROP`, `UPDATE` without `WHERE`, mass `DELETE`) | Medium | `Read-only` mode for every engine. `picklock` doesn't ask for confirmation (design decision). |
| Queries with sensitive data visible on screen | Low | That's the purpose of the tool; the user controls what runs. |
| Query results exported to disk (CSV/JSON, `Alt+E`) | Low | The user chooses the destination and the data; same trust model as the screen. Files use the default umask. |
| Logging of queries or passwords to disk | None | No logging to file. Errors are shown on screen. |

## Design decisions and accepted tradeoffs

### Passwords in plaintext in `connections.json`

`Ctrl+S` saves the connection in `~/.config/picklock/connections.json` (`0600` permissions). If the user chooses to save the password, it goes in **plaintext** in that JSON.

- **Why:** a TUI can't delegate to the system GUI in a portable way without a dependency; the OS keychain manager remains as future work.
- **Mitigation:** `0600`/`0700` permissions, optional password, and a masked field in the form.
- **Backlog:** integrate the system keychain (macOS Keychain, libsecret, Windows Credential Manager) or encrypt the file with a passphrase.

### SQL passthrough without confirmation

`picklock` executes the SQL exactly as the user writes it. `DROP TABLE`, `TRUNCATE`, or `UPDATE ... WHERE` without a condition run without asking for confirmation.

- **Why:** the user is the one writing the SQL and knows the database they're connecting to. Keyword-based confirmations would be a fragile and annoying heuristic (see LESSONS L-09).
- **Mitigation:** `Read-only` mode for every engine (SQLite `mode=ro`, PostgreSQL `default_transaction_read_only`, MySQL/MariaDB session read-only) as a safety net for production databases; the UI clearly shows which database you're connected to in the header. SQL Server has no per-session toggle: connect with a read-only user instead.

### Only one statement is executed

The editor executes the statement under the cursor (separated by `;`; if several
statements start on the same line, the first one is chosen). It never sends
multiple statements in a single round trip. This avoids the kind of accidents of
`multiStatements=true` (chaining destructive statements).

### MySQL/MariaDB: `multiStatements` disabled

The DSN never includes `multiStatements=true`. An SQL string with `;` doesn't become multiple statements.

### Identifiers always escaped

Table/column names are escaped with each engine's `QuoteIdent` dialect (`"x"`, `` `x` ``, `[x]`). Pagination `LIMIT`/`OFFSET` use integers generated by the browser, not user input. The editor SQL, on the other hand, is deliberately free: `picklock` doesn't rewrite it.

## Hardening implemented

- **`ConnectionConfig.ReadOnly`** — opens SQLite with `mode=ro` (no WAL or `busy_timeout`). A write returns a driver error. Persisted in saved connections. A global `--read-only` flag and a per-connection toggle now apply it to all engines (PostgreSQL via `default_transaction_read_only`, MySQL/MariaDB via a pinned `SET SESSION TRANSACTION READ ONLY`; SQL Server has no per-session toggle, so it shows a warning and relies on a read-only user).
- **`ConnectionConfig.SSLMode`** — PostgreSQL sets `sslmode` (`prefer` by default; `require`, `verify-ca`, `verify-full`, `disable`). MySQL/MariaDB and SQL Server expose the same field (`prefer`/`require`/`disable`) mapped to their driver TLS options, so connections that need encryption are no longer stuck with the driver default. Persisted in saved connections, and settable per invocation with `?sslmode=`/`?tls=` in a DSN.
- Validation of the `SSL` field in the form: invalid values prevent connecting.
- **Query timeout and cancellation** — queries run with a `context.WithTimeout`
  (configurable in the settings screen, `Ctrl+P`, persisted in `prefs.json`;
  default 60s) and can be cancelled with `Esc`. The context aborts the driver
  call, so a hung query no longer shows an indefinite spinner.
- **Persisted query history** — the last 100 queries are stored plaintext in
  `~/.config/picklock/history.json` (`0600`). A query may contain an inline
  credential (`USE ... PASSWORD`, `IDENTIFY BY`); the permissions mitigate it,
  but the user must not run queries with secrets in them if they share the
  machine. A heuristic filter was deliberately rejected (fragile, see LESSONS
  L-09).

## Security backlog

Ordered by impact:

1. **OS keychain** for saved passwords (removes the plaintext tradeoff).

## What `picklock` is NOT

- It's not a server and doesn't expose ports.
- It doesn't validate roles or permissions: it uses the credentials you pass it as-is.
- It doesn't encrypt traffic by itself: connection security depends on the engine configuration and the `SSL` field.
